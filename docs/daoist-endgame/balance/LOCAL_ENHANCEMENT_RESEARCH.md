# 本件基础强化与少量浮动词条研究

研究时间：2026-10-11。审计基线：`3e6bfce671b4c8099815dd2a4571e49fb3b5aa9c`，并读取当时工作区的 v3 目录；同一工作区有并行后续实现。本文记录研究发现与实施约束，不把建议冒充已经通过测试的功能。本文作者仅修改本文，没有修改运行时、目录、数据库或客户端，没有执行发布。

## 结论

1. 用户要的高百分比是“本件固有白字强化”。当前 `Attr47/13/15/17 + ModePercent(1)` 都进入人物总属性百分比桶，不能直接放入 D2 武器的数百百分比。
2. 当前服务端已存在可靠的本件局部计算先例：`ResolveRefineBonuses` 只取 `EquipDef.Base/Bonus` 的固有值，将百分比折为固定增量；物攻 47 必须分别折算最小/最大攻击。应复用这种局部语义，保留旧百分比词条。
3. SQL 能证明原生数据有攻击、防御、魔法攻击、魔法防御的百分比词条，不能证明存在另一组独立“xx强化”属性编号。应明确说明这是新功能采用本件作用域，不宣称已还原官方未取证机制。
4. 仙遗目前是单一 `UniqueRollBP` 联动全包，宿阵是完全固定。改为多数固定、少数明确范围是合理且可实现的；只把旧 4001 档线性映射到小范围，仍可能让满值只有 1/4001，必须专门设计离散采样或顶部满值区间。
5. 局部强化仍会随之后的全局装备百分比、状态百分比进入最终面板，这是正确层次；“只作用本件基础”约束的是强化的取值基数，不是把这部分最终伤害与全局增益隔离。

## 一、原生数据和当前运行时的证据

### 1. 已确认的属性

`server/internal/domain/equip.go` 定义：47 攻击、29 最小攻击、31 最大攻击、13 防御、15 魔法攻击、17 魔法防御，Mode0 固定，Mode1 百分比。

`server/migrations/000000_init-32.sql:30994` 起的 `game_equip_extra` 有明确例子：

- 1020 第0条：47 / 攻击 / 20 / Mode1 / 100% 生效
- 1020 第1条：19 / 命中 / 10 / Mode1 / 100% 生效
- 1024 第0条：47 / 攻击 / 10 / Mode1 / 100% 生效
- 1019 两条：29 最小攻击 +1、31 最大攻击 +3，均 Mode0

通过现有 `source_parser.py` 只读解析 `ov_card`、`ov_card_entry`、`game_equip_extra`，全部有名称的装备属性恰好是当前24个字典 ID。原始卡效果没有 14、16、18、20、30、32、48；不能猜相邻偶数是“强化”。全文搜索没有发现装备词条的独立“攻击强化/防御强化”名称。找到的“强化”还包含状态、技能、加工商店分类，不能混用。

这只是当前导入资料的边界，不足以否定用户对官方客户端文案的记忆。若之后拿到官方原始 tooltip 或权威属性定义，应另行比对；本次无须等待该资料才能做正确的本件功能。

### 2. 当前实际执行顺序

`Compute`（`equip.go`）的装备阶段：

1. `RefinedIntrinsic(st.RefineLevel)` 得到固有值加已折算的加工增量
2. 固有六维加到角色六维，固有二级属性加到固定桶
3. 模板固定词条、仙遗词条、天然随机词条、融合词条、孔内卡片快照、洗炼词条，统一经过 `applyAffix`
4. 被动词条进入同一桶；当前宿阵通过 scene 的 `passiveStatAffixes` -> `AstralBonuses` 从这里注入
5. 先应用六维百分比，再从六维派生二级；二级派生值、角色 Innate 和全部装备固定值合并后，应用装备/被动百分比
6. 状态单独累计：固定状态不被百分比状态反复放大；状态百分比基于完整装备基线

`applyAffix` 的百分比攻击使用一个共享 `pct.atk` 桶。47 只向这个桶记一次，最后同时作用上下限；29% 与31%也指向同桶。因此本件47不能转成两条百分比29/31再走这条路径，否则会重复放大两端。必须转成分别计算的固定增量，或在清晰分离的本件处理阶段计算。

`pctOf(v,p)` 现有写法为 `v + v*p/100`，其中乘法为 int32。这是现有全局代码，不应作为新数百百分比实现的安全算术模板。新局部乘法应先提升 int64，验证边界后饱和或拒绝。

### 3. 已有本件加工公式

`server/internal/domain/refine.go`：

- `ResolveRefineBonuses(e,effects)` 读的是未加工 `e.Base/e.Bonus`
- 百分比增量：`int64(base) * int64(percent) / 100`
- 结果超 int32 则返回失败；0增量省略
- 47展开为29与31，各自取相应固有攻击上下限
- 加工整级系数是该级总增益，不把前面所有等级再次相加
- `RefinedIntrinsic` 合入固定加工增量，不修改共享模板，也不合入卡、黄字、洗炼、融合或仙遗

Go 有符号整数除法向零截断。对正白字、正强化，等价于向下取整；不要笼统宣称负数也是 floor。

## 二、D2 一手资料：可借鉴之处与不可照抄之处

以下均为 Blizzard 的 Arreat Summit，访问日期2026-10-11；旧版本说明只能作为 D2 原始系统设计依据，不能用来断言所有 D2R 新版本细节。

- [Character Information](https://classic.battle.net/diablo2exp/basics/characters.shtml)：武器上的增强伤害直接改变武器伤害；装在护甲、头盔、盾牌里的增强伤害与人物属性、技能奖励进入另一阶段。最终伤害式使用已得到的武器伤害加额外伤害，再乘人物/技能等加成。
- [Basic Item Information](https://classic.battle.net/diablo2exp/items/basics.shtml)：武器先做百分比增强，随后加固定伤害。原生带增强防御的护甲以最大基础防御加1作为底数，再取整乘增强防御；无形基础奖励先于增强防御。
- [Unique Item Basics](https://classic.battle.net/diablo2exp/items/uniquebasics.shtml)：明确列出防御计算次序为基础（含无形）→增强防御→固定防御；不能在独特物品上组成符文之语。
- [1.10 Rune Words](https://classic.battle.net/diablo2exp/items/runewords-110.shtml)：展示大量固定词条加少量独立浮动项目。橡树之心仅全抗30–40浮动；石块增强防御250–290浮动，其余所列核心数值固定；刚毅增强伤害300%、增强防御200%固定，但生命成长和全抗有变化。CTA、精神等有多个浮动项，因此“每件只有一项”不是 D2 的普遍规则。
- [Rune Words](https://classic.battle.net/diablo2exp/items/runewords.shtml)：孔数、类型、顺序精确匹配；底材固有优势与符文之语一起保留。应参考分层与底材价值，不照抄所有具体数值。

本项目的建议公式是借鉴这种分层，而不是宣称一比一复制 D2：本项目 SQL 的白字已经固定，不应擅自套用 `maxac+1`、无形乘1.5或 D2 特有属性；D2 的防御和本项目防御都不可笼统解释成物理减伤百分比，本项目魔防与固定减伤更需要独立预算。

## 三、建议的本件强化契约

### 1. 作用域与类型

优先用独立明确的本件强化定义，复用现有目标属性语义，例如 LocalEnhancement{Attr:47,Percent:200}，或者新目录中 scope=item_base。空 scope/旧 Affix 必须保持原语义。与实现者协商最终字段后，生成器、服务器、协议与 UI 使用同一标记。

不要：

- 将所有既有 Mode1 重新解释成本件强化，会改变已保存的黄装、卡片、融合和技能
- 将新本件47混入 Passive 后期待还能知道是哪件装备
- 伪造未证实的原生 ID；若为了兼容三字段协议使用新内部 ID，必须明确它是新增项目编码并集中映射
- 将加成写回 `ItemDef.Equip.Bonus`，共享模板会污染其他同模板实例
- 在保存时覆盖原白字；白字、加工、局部词条应可重算、可脱下、可校验

首轮支持物攻、魔攻、防御、魔防。只在本件该项白字非0且主题相关时配置。首饰若确有魔攻15，可以有本件魔攻强化；无魔攻的头盔给“魔攻强化”是空词条，不能计入至少五条有用属性。

### 2. 精确建议公式

对每个装备实例 i、每个对应固有属性 s：

- B(i,s)：未加工的 `EquipDef` 固有白字
- R(i,s)：既有加工系统算出的固定增量
- L(i,s)：本件生效的新局部百分比之和
- D(i,s) = trunc0(int64(B(i,s)) * L(i,s) / 100)
- 本件白字贡献 = B(i,s) + R(i,s) + D(i,s)

随后才进入人物的固定加成、全局百分比、状态阶段。局部不乘 R、黄字固定值、仙遗其它固定值、卡片、星篆、洗炼、融合、人物六维派生值或其它装备。

如果一件装备有多来源同目标局部强化，建议先合百分比再取整一次。例如基础3、两条20%：合计40%增量1；逐条取整会得到0。加工已有独立取整契约，应保持其边界，避免此次顺便改所有旧精炼结果。两端攻击分别取整，不能先平均后还原。

在只允许非负局部增强的目录下，正数可写成 `B + floor(B*L/100)`。是否允许负局部属性应显式验证；本次没有需要引入负强化的新需求。

### 4. 宿阵必须保留实例归属与压制规则

`ActiveAstralRecipes` 返回 `Slot,UID,Item,Recipe`，每战/守/辅通道只选一个胜者，优先孔数、再小recipe ID、再小slot。独立星篆效果在宿阵被压制时仍有效。

- 不能对每个 `MatchAstralRecipe` 成功的装备都应用局部阵词条
- 只对已选中的 activation.UID 求局部增量
- 角色等级、职业、正确槽位、装备完好都必须通过原激活检查
- 禁用同通道宿阵时，应停止它的全包阵增益（包括本件强化），但不关闭独立符文快照
- 既有实现把普通阵词条注入 Passive；本件词条必须提前解析目标装备为固定增量，或让 Compute 接收带UID的局部加成
- 物品预览可展示潜在词条，已穿装备必须同时显示 inactive reason；不能把预览当作生效证据

## 四、浮动属性审计与“容易满值”方案

### 1. 当前基线

审计时1619件仙遗合计8816条附加属性、445个特性；1069件有5条属性，397件6条，143件7条，其余10件8–10条。1195件无特性，403件1个，21件2个。

- `ApplyUnique` 均匀抽取8000…12000（含两端，共4001种）
- `UniqueAffixes` 将每条Value都乘UniqueRollBP/10000
- 负面词条改用20000-roll，使高灵性减轻负面；攻速正负收益方向相反
- `ActiveUniqueTraits` 同时缩放所有PowerBP，阈值与目标不变
- 所有变化完全相关，并非每条独立掷骰
- 物品保存的是 UniqueID、UniqueRollBP、Revision；目录当前内容重新派生实际附加值
- 重铸从其余4000个BP均匀抽新值，可能变差；淬炼固定+500，最高12000，最差起点最多8次到满
- 40个宿阵所有额外属性和特性固定，无宿阵roll字段；独立星篆是卡UID上的固定快照

单次随机“灵性精确12000”概率1/4001，已有整数截断可能让部分低值词条提前看似满值，但不能把可见全满和元数据12000混称。

### 2. 推荐目录风格

默认全部固定。每件选择0–2个真正值得追逐的浮动项目，常见只1个；大多数额外属性、负面代价、特性幅度、触发阈值固定。浮动项可选择本件强化或关键主属性，其他身份属性稳定。

例：本件物攻强化180–200%，力量固定24，命中固定35，生命固定180，物理会心固定600BP；再加可选的固定有条件特性。显示明确下限/上限与当前值，不再把整件称80–120%缩放。

理论概率示例（仅设计例，不是现有D2的掉率证明）：

- 1个等概率整数180…200：满值1/21
- 2个独立范围200…220及10…12：全满1/(21×3)=1/63
- 2个独立的大范围会相乘变难；不要一边要求容易满、一边让每行独立101档
- 同一个质量档驱动1–2个浮动值，则完全相关，最高档可共同满；要在设计中承认这种相关性

### 3. 最小兼容方案：复用仙遗灵性，但只驱动明确浮动项

保留现有持久化字段和合法范围，为新版目录定义固定值与明确浮动范围。只给被选中的行使用 `UniqueRollBP`，固定行和固定特性不再乘灵性。旧实例保留BP排序，不额外修改其黄字、孔位、卡UID、加工、绑定、耐久或外观。

关键：`lo + (hi-lo)*(R-8000)/4000` 的上界只在 R=12000 出现，尽管界面范围小，满值仍为1/4001。要容易追满，可以采用21档：

- grade = min(20, floor((R-8000)*21/4001))
- value = lo + floor((hi-lo)*grade/20)
- R>=11811为最高档，190/4001约4.749%（约1/21）
- 旧R仍完全保存；10000恰好grade10；12000为grade20
- 若新生成直接在21档均匀抽样并存 `8000+200*grade`，每档恰好1/21，且都符合旧数据库检查

这是一种明确候选，非唯一实现要求。要避免重铸花钱后抽到另一个BP但同一可见档：新版重铸应排除当前可见档，或对重复结果有明确处理。淬炼+500会跨2–3档，而且R尚未12000时可能已全满；操作可用性与提示必须按新语义统一，不能向已满可见属性继续收取无收益费用。

### 4. 独立每行roll与宿阵roll的成本

若要求每条独立、未来目录调序不改变抽值，应保存稳定affix key对应的选值/档位和roll schema版本；只保存列表下标或在读取时调用随机源不安全。

宿阵目前 `unique_id=0` 时数据库要求 `unique_roll_bp=0`，不能借用仙遗字段。可选：

1. 本轮宿阵仍固定，把少量变量先用于仙遗。这最省迁移，但需要明确用户对符文之语浮动的要求是否必须立即覆盖。
2. 新增真正宿阵roll持久字段/表，在组阵完成时一次生成，保存recipe ID、roll版本与值；未插满时不重掷；重复请求按receipt重放。清孔、重组、换顺序必须定义何时重新付费抽值。
3. 以稳定UID+recipe ID计算可重现档位无需新字段，但这是“预定在底材上的结果”，不是组阵时随机，而且可能通过廉价试组预览结果。只有设计明确接受这种机制时才用，并在文档披露。

单独保存一个 seed 也需稳定算法和版本。不要把Revision当随机seed：插拔、交易、绑定等无关变化会意外重掷。

## 五、持久化、卡片与协议兼容

- 新本件定义来自目录，固定局部强化本身不需要改变物品UID或卡片快照。仙遗旧BP可以继续保存；只是目录版本有变化。
- 当前 `equipment_endgame_state` 外键指向durable item UID，迁移/读写验证在 `store/endgame_item.go` 和 `000000_init-50.sql`；所有新字段必须覆盖背包、穿戴、换装、仓库、摆摊、邮件/交易的物权流转。
- `CardInstanceState.StaticAffixes` 仅把Op1、概率100的原始快照作为一般词条；不得为新目录改写旧卡快照语义，也不得把模板未来数值自动灌到已存在的卡UID。
- 仙遗唤醒保留天然黄字。局部强化不能把天然黄字固定攻击纳入基础，但黄字全局攻击%之后可以放大全部白字贡献。这是重要的乘区组合，仍需对“同一满黄转仙遗”压力测试。
- 宿阵只接受天生无附加词条的普通底材；加工、洗炼、融合不因此变成天然黄字。新本件增强不能被误算成自然词条而破坏资格判断。
- 目前 EndgameStatView 只有attr/value/mode。若加scope/range字段，须检查闭合JSON schema客户端；旧客户端不能默认忽略新键。若选择项目内部新attr来保留三字段，也须同步名称、百分号、范围描述及所有校验。
- 物品tooltip、目录tooltip、已装备生效列表、实际战斗面板应来自同一解析函数，禁止UI自己重掷或重复缩放。
- 固定 trait 的 `Describe` 与 `ActiveUniqueTraits` 必须同步停止全包缩放，不能战斗固定而文字继续变。

## 六、验证清单

实施者需要提供下列实际测试结果；本研究本身未运行修改后的测试。

1. 单件本件+200%仅提升该件对应白字；另一件装备、人物六维、平加卡片不进入基数。
2. Attr47的上下限分别算一次；单独29/31定义不会通过共享攻击桶双算。
3. 本件0基础的词条配置拒绝或不计入有益线；不能用无效强化补足五条。
4. B=1/3等小数边界、多个局部来源、8000/10000/12000和新档位边界、int32最大值均覆盖；新乘法没有中途溢出。
5. 相同精炼条件下，精炼与局部加成相加、不互乘；既有精炼数值不变。
6. 仙遗保留黄字和孔位；旧卡实例快照逐字段不变；新词条仍受装备完好/等级门槛。
7. 同通道只一件宿阵能获得局部加成；被压制阵的独立星篆仍有效；脱下/损坏/修复后重算正确。
8. 固定行、固定负面、固定特性在最低/中间/最高质量完全相同；仅声明的1–2项浮动。
9. 随机生成、重铸、淬炼、重复请求重放、重登录、交易/仓库/邮件后结果稳定；没有免费再掷骰路径。
10. 概率/档位枚举验证“满值容易”的真实发生率；用实际可见属性判定是否满值，不能只检查BP。
11. 1619仙遗与40宿阵的既有新鲜仙遗/同黄转仙遗/实际原生黄装基准全部重算，不能沿用旧全局百分比的通过报告。
12. 同额卡/孔投资另做对比；全套装备和大卡压力测试独立于单件自然黄装地板。源池外底材仍标暂定锚点，不能伪造原生同级黄装。

## 实施选型摘要

推荐最小语义改变：保留旧全局百分比；为新内容增加显式本件攻防强化；只读未加工固有白字折算固定增量；宿阵仅winner UID生效；固定多数属性，只有明确1–2个范围追满。仙遗复用持久BP并使用粗档位是低风险选项；宿阵若需要浮动，应明确选择真正持久roll或公开的底材确定档位，并测试其重组边界。
