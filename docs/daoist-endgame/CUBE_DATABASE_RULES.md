# 周天鼎配置回归数据库

## 数据来源与职责

`000000_init-61.sql` 把既有 66 个配方迁入三张标准配置表：

- `game_cube_recipes`：原配方 ID、名称、operation、说明、是否要求装备目标、铜币、转篆投料枚数、淬炼品质步长，以及材料/产物行数。
- `game_cube_materials`：按序排列的物品 ID、消耗数量；物品外键引用 `game_items`。
- `game_cube_outputs`：按序排列的产物物品 ID、基础数量、等级上限、等级除数、数量倍率；物品外键引用 `game_items`。

产物数量为 `(基础数量 + min(max(装备等级, 0), 等级上限) / 等级除数) × 数量倍率`，其中除数为 0 时不加等级项。计算使用 int64，结果必须在正 int32 范围内。原普通装备分解为 `8 + min(max(等级,0),100)/5` 星髓，暗金为三倍星髓及 4 八仙余韵，星篆分解为 4 星髓。数值没有重新平衡。

`data.LoadCubeRules` 通过只读 Querier 在开服时加载到不可变 `domain.CubeRuleTable`。配方和子行在返回前全部校验；缺表、缺既有配方、子行缺失、重复数据、不支持的 operation、未闭合物品、非法数量均报错。访问器返回深拷贝，生产环境不会读迁移文件，也不使用硬编码配方作为缺失配置的替代品。

`CubeContext.Rules` 注入配方，`CubeContext.Catalog` 注入暗金/星篆/宿阵目录。目录展示和预览/执行消费同一张规则表。配置在开服时冻结；修改 SQL 配置后需要按既有流程重启服务，不会改变已签发预览中的运行时快照。

执行内核仍是 Go：仅运行预定义操作、背包归属和锁定检查、材料扣除、孔位/卡片身份、真实容量检查、随机源、实例 UID、预览指纹与原子提交。数据库配置不能提供脚本、任意 SQL 或绕过这些约束。原配方 ID 与既有物品 UID、存档字段、旧版属性不变。

## 可重复迁移

必须与其他初始化分片一样在事务中应用，失败时回滚该批；不能先提交配方 header 再另行提交子表。升级发布应将代码和所需迁移成对部署，回退也须成对处理，避免旧版本服务读取不匹配的配置。

每个配方只在第一次插入 header 时写其材料与产物。重复迁移既不会覆写管理员改过的费用或数量，也不会补回管理员已删除的材料行。若管理员修改了子行数，必须同步调整 header 的 `material_count` / `output_count`；否则开服加载拒绝不完整配置。迁移不改角色、背包、装备实例和回执表。

## 验证

- SQL 中的 66 条配方与迁移前 Go 配方渲染金样逐字段比较：ID、名称、operation、说明、材料、铜币、是否需要目标、星篆产物。
- 原分解公式以负数、0、临界等级、50/60/100/200 级独立验证。
- 修改注入的费用、材料、产物公式、品质步长验证真正影响执行，避免只修改目录展示。
- 规则快照不可变；缺配置 fail closed；坏引用、未知 operation、非法数量、重复/缺失子行有拒绝测试。
- 既有全配方预览/执行、RNG/UID 次数、背包容量、锁定、持久化重放与事务回滚测试继续作为兼容性门禁。

显式真实 PostgreSQL loader 验证入口：设置 `FANTASY_CUBE_PG_DATA` 为独立且空闲的测试集群、`FANTASY_CUBE_PG_DATABASE` 为测试库、`PG_BIN` 为受信 PostgreSQL 工具目录，然后运行 `go test ./internal/data -run '^TestCubeActualPostgresLoader$' -count=1 -v`。它只通过只读事务执行 `LoadItems → LoadCubeRules`，不启动守护服务，不建库，不连接应用数据库。
