# 洞天怪物数量再翻倍（迁移 76）

## 生效范围

迁移 `000000_init-76.sql` 将洞天规则版本 1 原样复制为已发布版本 2，只增加 `floor_population_multiplier = 2`，并把仍指向版本 1 的新局选择器切换至版本 2。生命、伤害、难度层级、时间、进度值、掉落规则、结算奖励和钥匙消耗均不改变。发布版本仍不可修改。

新开的洞天每层普通怪、蓝精英、黄精英分别精确翻倍：

- 原来总数 96–160，调整为 192–320。
- 蓝精英 6/9/12 调整为 12/18/24。
- 黄精英 2–4 调整为 4–8。
- 最终守关首领仍为 1 个。

已有局绑定原有规则版本。旧存档中没有该字段或值为 0 时仍为原密度；切换数据库当前规则不会改变该局后续楼层密度。已经保存的楼层计划继续直接使用，不重新生成、不原地补刷。数据库升级和服务端更新后，新局才采用翻倍规则。

## 确定性与地形

新版计划编号为 3，但保留 v2 基础种子流：地图、入口、出口、原有怪物顺序/位置/类型、精英类别和首领完全不变，再使用独立确定性随机流，给每个原有怪物追加一个同类别、同外观模板的怪物。新增对象由正常分配器获得新的实体标识；原有精英的技能种子及顺序保留。

额外坐标只能来自已通过原生碰撞 MASK 和连通分量校验的位置。常规地图继续使用 64px 网格；仅候选位置不足的紧凑地图生成与原网格对齐的 32px 补充网格。所有出生点与入口至少相距 160px、与出口至少相距 80px，原生目录中任意两出生点至少相距 32px。

若某个自定义地图没有足够坐标，生成器在扣钥匙/保存换层前按确定顺序尝试其他地图，绝不静默把翻倍数量压回旧上限。全部地图不满足时明确拒绝生成。

## 数量、上限与进度

保存计划的 v1 上限仍是 64，v2 上限仍是 160，v3 上限是 320。线协议的保守校验包络扩大到 320 个普通/精英实体加一个首领、24 个蓝精英、8 个黄精英；客户端已有 2048 条光环和 1024 个进度球的上限，不需要修改客户端数据协议。

总进度仍为 10,000，普通怪仍给 40，蓝精英仍掉 1 个、黄精英仍掉 4 个每个 200 的进度球。因此同一层可提供的进度也精确翻倍。按当前规则，单层完整清怪并拾取进度球足以召唤首领；不再需要通过怪物数量不足来强制玩家换层。达到进度后仍按既有流程清场并生成唯一首领，结算奖励不翻倍。

## 验证结果

- 原始 SQL + MASK 静态目录：保留全部 189 张地图，每图生成 1–150 楼，共 28,350 个计划，全部通过与 v2 的精确逐项比较、无重叠、出生安全距离和 32px 最小间距检查。
- 数量为 192–320，均值 260.12；对应原均值 130.06。
- 只有地图 28402「凝香冢」需要补充候选：原有 231 个坐标，再增加 697 个已验证坐标。其他 188 张地图没有新增候选网格。
- 运行时加载器的独立狭窄地图用例：110 个原坐标 +334 个补充坐标，连续 150 个楼层计划均可精确翻倍，仍在碰撞连通区内。
- 场景实刷覆盖地图楼层 1/150 × 难度 1/150，检查全部实体数量、各类别血量缩放、原精英技能分配、唯一首领、重复死亡事件不会重复进度/进度球/奖励。
- 保存计划 JSON 往返逐字节一致；旧局在当前规则切换后仍保持原密度，新局使用新密度。
- 隔离 PostgreSQL 通过迁移 75→76、事务回滚、重复执行、配置仅密度变化、发布版本不可修改、重放不会覆盖运营者较新的当前版本；真实 `LoadItems → LoadLootRules → LoadRiftRules` 通过，旧规则快照完全保留。
- `go test ./internal/domain ./internal/game/scene ./internal/data` 通过；新增几何、场景与存档定向用例另行通过。新增确定性、紧凑地形、旧局兼容、实刷和重复死亡用例的 `-race` 检查也通过。完整仓库最终检查由整合任务统一执行。

## 独立性能对照

在共享云测试机、相同地图/种子下比较 1× 与 2×，不混入客户端改动。结果是加载阶段诊断，不是客户端帧率或满负载战斗保证：

- 生成计划，5 次 Go benchmark 中位数：约 0.84ms → 3.50ms；分配约 254KB → 627KB，42 →71 次分配。
- 实际场景生成并清理 160/320 个实体，每组 100 次、重复 5 组，中位数约 1.17ms →3.04ms。
- 共享测试机有其他检查并发，计时存在明显波动；分配量和精确实体数量更稳定。未做 Unity 客户端帧率、联网实机或生产服压测。
